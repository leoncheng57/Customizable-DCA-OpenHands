Why Agentic Coding Tools Are Fast

…and whether OpenHands with the context condenser achieves the same speed.
Research compiled August 2026 · sources: vendor engineering blogs & docs, Terminal-Bench 2.1, Artificial Analysis, EvoClaw-Bench logs, OpenHands SDK v1.40.1 source, and this repository's deployment.

TL;DR. Speed in agentic coding tools comes from seven levers, roughly ordered by impact: reasoning-token budget, agent turn count, prompt caching, model decode speed, fast edit application, parallelism, and environment overhead. Cursor, Claude Code, Codex, OpenCode, and Amp each pull a different mix of these. OpenHands' LLMSummarizingCondenser addresses exactly one of the seven — unbounded context growth on long trajectories — where it works well (up to 2× per-turn cost cut, quadratic→linear scaling, success rate preserved). It does not close the gap on turn count, parallelism, or reasoning budget; a cross-harness benchmark with the model held constant still measured OpenHands at ~3.1× the wall-clock of Claude Code.

Evidence labels used throughout: verified independently measured or primary source with methodology · vendor claim self-reported by the tool's maker · anecdotal single-operator or community test.

1. The speed factor taxonomy

An agent loop is: model generates (thinking + tool calls) → tools execute → results appended → repeat. Every factor below attacks a different term in that loop's latency equation.

  1. Reasoning-token budget — the dominant latency term for frontier reasoning models. Artificial Analysis measured Claude Sonnet 5 at max effort: 86.6 tok/s decode but 150.65 s time-to-first-answer-token vs a 2.8 s class median — thinking time, not decode speed, dominates perceived latency. verified
    Every fast tool exposes an effort dial: Codex minimal→xhigh, Claude Code /effort, Amp's Rush mode ("GPT-5.5 with no reasoning — twice as fast" vendor claim).
  2. Number of agent turns — each tool call is a full API round trip carrying the whole transcript. EvoClaw-Bench (raw logs published) held the model constant: Kimi-K2.6 issued 5,044 turns on OpenHands vs 2,446 on Claude Code and took 3.1× the wall-clock — attributed to tool inventory mismatch (no Grep/Glob/paginated-Read that models were trained on) and prompt-induced test-thrashing (pytest run 9.2× more often). verified
  3. Prompt caching — cache reads price at 0.1× input with TTFT reductions up to ~75–85% on long prompts (Anthropic docs). Real Claude Code sessions show ~95% of input tokens as cache reads; xAI reports >90% hit rates in coding harnesses; Codex-family models get 24-hour cache retention. Cache invalidation is the flip side: switching models, changing tool definitions, thinking config, or speed tier throws the prefix away. verified
  4. Model decode speed (tokens/sec) — spans >20× across models (86.6 tok/s Sonnet 5 → 1,932 tok/s Celeris-1, per Artificial Analysis verified). Cursor Composer claims "4× faster than similar models" vendor claim; grok-code-fast-1 launched at 190 tok/s vendor claim; Anthropic fast mode sells 2.5× output tok/s on the same Opus weights at 2× price.
  5. Fast edit application — frontier models are unreliable at diff formats (line numbers tokenize badly; diffs are out-of-distribution), so Cursor splits plan (frontier model) from apply (a fine-tuned full-file-rewrite model at ~1,000 tok/s using "speculative edits", ~13× over vanilla inference). vendor claim (methodology published)
  6. Parallelism — parallel tool calls within a turn and parallel subagents across contexts. Anthropic's multi-agent research system cut research time "up to 90%" — with the explicit caveat that coding parallelizes less well than research. vendor claim Cursor RL-trained Composer to "maximize parallelism whenever possible" in tool use.
  7. Environment overhead — sandbox/container startup, approval-prompt round-trips, tool-listing timeouts. OpenAI cut Codex cloud median task completion by 90% via container caching vendor claim; Amp removes approval prompts by default; Codex's kernel sandbox (Seatbelt / Landlock+seccomp) makes unattended full-auto loops safe, eliminating human round-trips. This is the weakest-quantified factor in public data.

4. OpenHands + condenser: does it achieve the same speed?

Verdict: No. The condenser solves one specific problem — unbounded context growth on long trajectories — which is one of the seven speed factors. It brings OpenHands to parity with what Claude Code's auto-compaction and Codex's native compaction already do, but leaves turn count, sequential tool execution, parallelism, and reasoning budget untouched. Cross-harness data (EvoClaw) still shows ~3.1× the wall-clock of Claude Code at the same model.

What the condenser is

LLMSummarizingCondenser (SDK v1.40.1 source, verified):

  • Trigger — fires when history exceeds max_size events (soft) or total tokens exceed max_tokens (hard), or on explicit request (e.g. after a context-window-exceeded error).
  • Action — keeps the first keep_first events (system prompt + task) and a recent tail; replaces the middle with one LLM-written summary event. Targets ~half the threshold so it doesn't re-fire every step. Summaries are re-summarized in later condensations. A hard_context_reset fallback summarizes the entire view with truncation retries.
  • Costs — each condensation is an extra LLM call (billed under a separate condenser usage key), consumes an agent turn, and — per the SDK's own README — "condensation destroys the prompt cache, but doing so regularly keeps the cost of rebuilding the prompt cache low."

Measured effects verified

  • Cost: up to 2× per-turn API cost reduction once condensation kicks in; cumulative cost scaling goes from quadratic to linear in conversation length (All Hands blog, Apr 2025).
  • Latency: "consistent response times in long sessions"; benchmark tasks solved with less money, fewer tokens, and less completion time. No single latency multiplier published — but this deployment's own measurement (issue #48) was 4× slower per step at 100–200k tokens/turn before enabling the token trigger, so the effect on long sessions is real and large.
  • Quality: 54% vs 53% on a SWE-bench Verified subset — success rate preserved, not improved. The only trade-off is slightly more turns (the condensation turns themselves).

What the condenser does not optimize

Turn count / tool design

  • EvoClaw's 3.1× wall-clock gap is tool inventory + prompt behavior, not context length.
  • No Grep/Glob/paginated-Read tools that models were RL-trained against.

Sequential execution

  • SDK 1.40 tool_concurrency_limit defaults to 1 (sequential).
  • Steps are strictly sequential; no parallel subagents.

Per-step model speed & reasoning budget

  • Model-agnostic passthrough — nothing like Codex's adaptive thinking or Cursor's fast-apply model.
  • Below 80k tokens / 240 events the condenser never fires: zero effect on short sessions.

Environment overhead

  • Fixed per-run stalls (e.g. a dead MCP server's 20 s tool-listing timeout, issue #41) are out of reach.
  • Classic OpenHands V0 per-conversation Docker startup is a fixed cost it cannot touch.

  • This deployment's condenser probe reflects the local agent-canvas 1.12 / SDK 1.40.1 state; stock installs ship max_tokens: null (token trigger off).
